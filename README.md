# Trend Hunter Puzzle

## 运行方式

在项目根目录安装依赖（若未安装）：

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```
运行评测命令：

```bash
python run.py --input voices.jsonl --as-of 2026-07-24 --out trends.json
```
# 默认的 `hybrid` 模式会在本地完成候选发现与统计分析；如果运行环境提供 OpenAI 或 Jev API Key，只会将少量入围候选交给外部模型进行语义复核和标题优化。没有 API Key 时，整个流程仍可完整离线运行，建议先使用不接入 API KEY 的版本。

# 1. 核心思路：Cross-disciplinary Modelling Strategy

我的方案借用了几个其他学科里已经非常成熟的思路，并把它们重新应用到玩家社区趋势识别中。

- **Minimum Description Length（MDL）· 信息论**  
  判断不同说法是否值得被解释成一个新的独立话题。

- **Topic \(R_t\) · 流行病学**  
  判断一代参与者之后，是否不断出现新的参与玩家。

- **CUSUM · 工业过程控制**  
  发现没有单日爆发、但持续缓慢升温的问题。

- **事件残差、压力测试和真实性检查**  
  用来区分版本日噪声、单一来源放大、重复文案和疑似协调传播。
  
每一种方法只回答自己最擅长的问题，最后再进行证据融合。

这里有一个**刻意的设计**：

**Status 和 Ranking 是两个完全不同的问题。**

Status 回答：

> **“这个故事正在发生什么变化？”**

Ranking 回答：

> **“游戏工作室现在应该优先看哪个问题？”**

例如：一个传播速度很快的角色昵称梗，可能拥有很高的 \(R_t\)；但一个增长速度较慢的登录故障，仍然可能因为影响严重、行动价值高而排在它前面。

## 状态是怎样判断的

任何单一指标都不能直接宣布：

> “这是一个 Growing trend。”

例如，`growing` 的初始证据组合为：

```text
Growing
= 0.40 × Rt 增长证据
+ 0.35 × CUSUM 持续性
+ 0.15 × 事件调整后持续性
+ 0.10 × 参与者广度
```

不同状态使用不同的证据组合，因为它们回答的是不同问题。

### `new`

最近刚刚形成一个具有独立意义的新故事，但历史数据还不足以判断未来走势。

### `growing`

不仅有新的独立玩家加入，而且讨论在时间上具有持续性。  
仅仅 \(R_t\) 很高并不足够。

### `fading`

话题过去确实成立，但新参与者数量和持续声量正在下降。

### `one-off`

话题在短时间内集中爆发，并且已经观察到明显的峰后衰减，也没有形成下一代参与者。

### `not real`

复制、时间同步、来源集中和压力测试坍塌等多种异常同时出现。

这里的 `not real` 表示传播模式值得单独审查，并不代表系统能够证明具体是谁在操纵。

当证据不足时，系统内部允许保持 `undetermined`，而不是强行给候选分配状态。

## 工作室优先级是怎样计算的

排名回答“此Trend值不值得现在优先处理”，此 Trend 是否满足**重要、当前、可信、具体、可行动。**

基础优先级为：

```text
Priority Base
= 0.25 × Impact
+ 0.20 × Momentum
+ 0.15 × Breadth
+ 0.15 × Robustness
+ 0.10 × Novelty
+ 0.10 × Timeliness
+ 0.05 × Actionability
```

其中：

- `Impact`：问题对玩家体验或损失的影响；
- `Momentum`：趋势当前是否仍在增强；
- `Breadth`：是否由多个独立玩家、平台和频道共同支持；
- `Robustness`：去掉最大账号、最大平台、峰值日和重复文案后是否仍成立；
- `Novelty`：是否真的出现了一个新的玩家故事；
- `Timeliness`：最近是否仍在活跃；
- `Actionability`：游戏团队能否根据这些信息直接去检查某个具体机制或系统。

# 2. 什么内容应该被放在一起？

**自己创造新的话题类别，而不是把评论塞进预先定义好的分类。**

系统首先清洗并统一简繁体、网络用语和图片等噪声，再通过 `parent_id` 补全短回复的上下文；随后将每条评论转换为结合词语、字符组合与低权重玩家词库提示的语义向量，并通过无预设类别的聚类自动发现玩家故事。

初步聚类后，系统会综合**语义相似度、具体产品机制、玩家重叠、工作室需要采取的行动以及趋势所处的生命周期**，判断哪些评论真正属于同一个问题；仅仅共享关键词或大类并不足以合并。

最后，LLM 在可用时只负责复核候选、排除语义混杂、优化标题与行动建议，而趋势分组、状态、日期和证据仍由本地算法决定。

# 3. 从原始消息到最终趋势

最终结果描述了一个**具体玩家故事**，而不是只告诉工作室它属于什么大类。

例如，如果证据足够，我更希望输出：

> **“Boss 战中自动索敌频繁锁向小怪，开始影响玩家操作。”**

而不是：

> **“战斗体验问题。”**


因此，我在列出 Category 的基础上，在最终输出中添加了代表性玩家**原话**。

代表评论会优先选择：

- 能完整说清问题的；
- 明确指出产品机制的；
- 接近该话题语义中心的；
- 来自不同玩家、时间、平台和频道的。

# 4. 8 月底《星环守望》的玩家社区发生啥了

到 8 月底，停服维护引发的登录转圈、排队和掉线已经逐渐降温，但周年节点放大了游戏长期积累的信任问题。外挂、锁头和举报无反馈虽然不再快速吸引新参与者，却已经从单局体验问题演变成对竞技环境的长期不信任。与此同时，抽卡讨论也从“个人运气差”转向质疑更新是否暗改概率、保底机制是否透明，说明不同玩家群体正在反复遇到并重新讨论同一类付费信任问题。

此外，“霜月皮肤”的大量正面声量中约96%属于重复文案，去重后只剩约5%，不应被当作自然口碑增长。综合来看，8月底最重要的变化不是某个Bug突然爆发，而是竞技公平、付费透明度和运营沟通正在汇合为同一个更深层的问题：玩家是否仍然信任工作室。公司应优先公布可验证的结果，包括维护复盘与补偿依据、举报处理反馈，以及抽卡配置和近期变更说明。

## 5. 我尝试过但没有保留的方法（迭代）

- **过度筛选早期趋势：** 早期版本太偏向已有大量历史证据的成熟话题，导致六月和版本刚更新时经常漏掉真正的新信号；后来将“值得注意”和“已经证明在增长”拆开处理。

- **过度抽象与重复趋势：** 宽泛的 category 会把具体玩家故事压成“抽卡公平”“技术体验”等大类，同时相近故事有时会重复进入 Top-K；后来改为围绕具体产品机制、原始证据和工作室行动进行去重与命名。

- **对版本事件处理过于极端：** 不做调整时，版本日的正常尖峰容易被误判为趋势；惩罚过重时，又会把真实的版本后问题一起过滤，因此最后改用 Event Residual 判断事件结束后仍然存在的额外讨论。

- **关键词、情绪或 LLM 单独解决都不够：** 关键词和情绪分析无法还原真正的玩家故事，而让 LLM 直接读取全部数据又难以复现、成本高且更容易产生未来泄漏；最终这些方法都只作为辅助，而不是核心决策。

## 6. Limitations 这套方法目前存在的已知限制

- **真实性检查只能识别可疑传播模式。** 数据中没有完整的曝光、转发、社交关系，也没有真实账号创建时间、点赞或曝光量，因此系统只能通过重复文案、时间同步、来源集中和压力测试坍塌等间接信号判断异常传播，不能证明具体存在水军，也不能确定是谁在影响谁。

- **早期趋势天然更不稳定。** 数据积累较少时，CUSUM、Topic \(R_t\) 和长期持续性证据都会更弱，因此系统可能低估刚刚出现但尚未成熟的话题。后期可以加入其他判断模型进行辅助支持。

- **语义聚类仍可能过度合并或过度拆分。** 特别是当同一个问题在不同阶段换了说法，或者多个产品机制被玩家串成同一个故事时，自动聚类不一定总能准确恢复真实边界。

- **Lexicons 只是辅助，不是答案。** 玩家黑话词库可以帮助系统理解“刮痧”“歪了”“坐牢”等表达，但遇到完全新的梗或新说法时，系统仍然需要依靠语义表示和自由聚类自行发现。

- **权重和阈值仍然是启发式设定。** 当前评分经过历史 `as-of` 回测和边界测试，但没有人工标注的 ground truth，因此这些分数不能被理解为真实概率或准确率。
